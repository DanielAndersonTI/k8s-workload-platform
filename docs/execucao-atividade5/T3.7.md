## Objetivo

Confirmar que a cota de CPU pedida ao nó existe no cgroup e separar esse limite da capacidade que o kubelet anuncia.

## Comandos

```bash
docker inspect minikube --format '{{.HostConfig.CpuQuota}} {{.HostConfig.CpuPeriod}} {{.HostConfig.NanoCpus}} {{.HostConfig.Memory}}'
docker update --cpus=3 minikube
docker exec minikube cat /sys/fs/cgroup/cpu.max
docker exec minikube cat /sys/fs/cgroup/memory.max
kubectl describe node minikube
kubectl top node
```

## O que aconteceu

Antes do ajuste, `cpu.max` valia `max 100000`, apesar do `--cpus=3` passado ao `minikube start`. O `docker update --cpus=3` criou `CpuQuota=300000` e `cpu.max` passou a `300000 100000`. A memória já estava limitada a 6 GiB desde a criação. O kubelet continuou anunciando 4 vCPU e 8131812Ki, e `kubectl top` calcula o percentual sobre esse total.

## Saída

```text
0 0 0 6442450944
max 100000
0 0 3000000000 6442450944
300000 100000
6442450944
  cpu:                4
  memory:             8131812Ki
minikube   406m   10%   712Mi   8%
```

## Decisões

O `20-cluster.sh` passou a aplicar o limite com `docker update` e a encerrar com erro se `CpuQuota` continuar zero. A alternativa, aceitar o `--cpus` sem efeito, produziria um relatório falso sobre o dimensionamento.

## Problemas

O `--cpus` do driver Docker não cria cota no minikube v1.39.0. O limite só existe depois do `docker update`, que ficou registrado no script.
