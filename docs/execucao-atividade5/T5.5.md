# T5.5 — Coletar logs, eventos e estado das sondas

| Campo | Valor |

| Data | 23/11/2026, 20:36 UTC |
| Fase | Fase 5 |
| Status | concluída |
| Evidências | `T5.5-logs.txt` |

## Objetivo

Verificar o que os processos registram, como o kubelet descreve as sondas e quais eventos acompanharam a falha de imagem.

## Comandos

```bash
kubectl -n workloads logs -l app.kubernetes.io/name=cpu-workload --tail=8 --prefix
kubectl -n workloads get events --sort-by=.metadata.creationTimestamp | tail -25
kubectl -n workloads describe pod <pod>
kubectl -n workloads logs <pod> --timestamps | grep -c Traceback
```

## O que aconteceu

Os pods de CPU registram apenas a linha de início na porta 8000. Os pods de memória e de I/O acumularam três tracebacks de `ConnectionResetError`, todos quando o cliente encerrou a conexão antes da resposta. O processo continuou atendendo e o contador `failed` permaneceu zero. O `describe` confirmou as três sondas em `/health` e os limites de 1 vCPU e 512 MiB no perfil de CPU.

## Saída

```text
cpu application listening on port 8000 (max 32 concurrent work units)
Liveness:   http-get http://:http/health delay=10s period=20s failureThreshold=3
Readiness:  http-get http://:http/health delay=0s period=10s failureThreshold=3
Startup:    http-get http://:http/health delay=0s period=2s failureThreshold=15
3
```

## Decisões

O arquivo de evidência guarda a contagem de tracebacks e a explicação, em vez de omiti-los. O erro é do cliente que abortou a conexão, não do servidor, e não alterou nenhuma resposta observada.

## Problemas

Os tracebacks de conexão abortada poluem o log. A correção exigiria tratar `ConnectionResetError` no servidor e reconstruir as imagens; ficou registrado como limitação.
