## Objetivo

Fechar o namespace com a política `restricted`, impedir que um rollout voluntário derrube as duas réplicas e definir recursos padrão para containers que omitem pedidos.

## Comandos

```bash
kubectl apply -k k8s/
kubectl -n workloads get pdb,limitrange
kubectl get namespace workloads --show-labels
kubectl -n workloads run psa-test --image=busybox:1.36 --restart=Never -- sleep 5
kubectl apply -f /tmp/lr-test.yaml
kubectl -n workloads get pod lr-test -o jsonpath='{.spec.containers[0].resources}'
```

## O que aconteceu

O namespace recebeu as quatro etiquetas de Pod Security Admission. Os três PDBs ficaram com uma interrupção permitida cada. O pod `psa-test`, sem contexto de segurança, foi rejeitado com a lista de quatro violações. O pod `lr-test`, compatível com o perfil e sem `resources`, recebeu `requests` de 100m/128Mi e `limits` de 500m/512Mi do LimitRange. Os seis pods da aplicação continuaram `Running` e os três EndpointSlices mantiveram dois endereços cada.

## Saída

```text
namespace/workloads configured
limitrange/workload-defaults created
poddisruptionbudget.policy/cpu-workload created
poddisruptionbudget.policy/io-workload created
poddisruptionbudget.policy/memory-workload created
Error from server (Forbidden): pods "psa-test" is forbidden: violates PodSecurity "restricted:v1.37"
{"limits":{"cpu":"500m","memory":"512Mi"},"requests":{"cpu":"100m","memory":"128Mi"}}
```

## Decisões

O PDB usa `minAvailable: 1` com duas réplicas, o que permite uma interrupção voluntária por vez. O LimitRange não altera os pods existentes; ele vale para containers criados depois, por isso o teste com `lr-test`.

## Problemas

Nenhum. O `kubectl apply -k` reaplicado depois do rollback mostrou os PDBs como `configured`, por diferença na anotação `last-applied`; os objetos permaneceram corretos.
