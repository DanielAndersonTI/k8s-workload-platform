# T7.11 — Reiniciar um container pela sonda de liveness

## Objetivo

Provocar a falha da sonda de liveness no `cpu-workload` e observar o reinício do container sem retirar o pod do Service.

## Comandos

```bash
kubectl -n workloads patch deployment cpu-workload --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/livenessProbe/httpGet/path","value":"/sem-sonda"}]'
kubectl -n workloads rollout undo deployment/cpu-workload
```

## O que aconteceu

Depois do rollout com o caminho inexistente, a base de restarts das duas réplicas novas era zero. Aos 57 s, o contador máximo chegou a 1 nas duas réplicas, e os eventos registraram `Liveness probe failed: 404` seguido de `Container app failed liveness probe, will be restarted`. O `rollout undo` devolveu a sonda para `/health` e a porta 8600 respondeu 200.

## Saída

```text
base de restarts depois do rollout: 0
t+46s restarts max=0
t+57s restarts max=1
Killing   Container app failed liveness probe, will be restarted
Unhealthy Liveness probe failed: HTTP probe failed with statuscode: 404
health 200
```

## Decisões

A sonda de readiness continuou apontando para `/health`, e por isso o pod permaneceu no Service durante o reinício do container. Sem essa separação, o teste mediria a retirada do endpoint, não a ação do kubelet.

## Problemas

A primeira execução partiu de pods com dois restarts herdados do reinício da VM e encerrou no primeiro ciclo, sem observar o evento. A correção foi medir a base depois do rollout e esperar os pods antigos saírem.
