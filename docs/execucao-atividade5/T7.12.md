# T7.12 — Reiniciar a VM e recuperar o cluster

| Campo | Valor |

| Status | concluída |
| Evidências | `T7.12-reboot.txt` |

## Objetivo

Verificar o que volta sozinho depois do reinício da VM e qual é o caminho de recuperação do cluster.

## Comandos

```bash
sudo systemctl reboot
systemctl is-enabled docker
docker inspect -f '{{.HostConfig.RestartPolicy.Name}}' minikube
docker start minikube
minikube stop && minikube start
```

## O que aconteceu

O Docker está habilitado no boot, mas o container do Minikube tem política `no` e ficou em `Exited (137)`. Um `docker start` isolado deixou o container em execução e o kubelet parado. Depois de iniciar o kubelet, o nó voltou a `Ready` e os seis pods ficaram `Running`, porém as NodePorts respondiam 000 e o CoreDNS ficou em 0/1.

A causa foi a perda das entradas `control-plane.minikube.internal` e `host.minikube.internal` em `/etc/hosts` do nó, que o driver Docker do Minikube recria no `minikube start`. Com o `minikube stop` seguido de `minikube start`, o kube-proxy voltou a alcançar o apiserver, o CoreDNS passou a 1/1, as portas 8000 a 8002 mantiveram o mapeamento e as três URLs externas responderam 200.

## Saída

```text
systemctl is-enabled docker: enabled
RestartPolicy: no
minikube Exited (137)

coredns 0/1 Running
lookup control-plane.minikube.internal on 192.168.49.1:53: no such host

minikube start:
192.168.49.2    control-plane.minikube.internal
192.168.49.1    host.minikube.internal
8600 200 / 8601 200 / 8602 200
```

## Decisões

A recuperação passou a usar `minikube start` em vez de `docker start`, porque a primeira preserva o mapeamento de portas e refaz o DNS do nó. O script de testes ganhou o modo `after-reboot` para conferir o retorno sem depender da CLI do OpenStack.

## Problemas

Não há retorno automático: o container não sobe no boot e o kubelet não volta com ele. Quem reiniciar a VM precisa rodar `minikube start` e conferir as três URLs antes de qualquer medição. A sessão de OpenStack da VDI também expirou, e o reboot foi feito por SSH.
