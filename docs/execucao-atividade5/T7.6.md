# T7.6 — Atualizar com imagem inválida e executar rollback

## Objetivo

Verificar o comportamento de `RollingUpdate` com `maxUnavailable: 0` quando a imagem nova não existe, e o efeito do `rollout undo`.

## Comandos

```bash
kubectl -n workloads rollout history deployment/cpu-workload
kubectl -n workloads set image deployment/cpu-workload app=danielandersonss/poi-cpu:nao-existe
kubectl -n workloads rollout status deployment/cpu-workload --timeout=10s
kubectl -n workloads rollout undo deployment/cpu-workload
kubectl -n workloads rollout status deployment/cpu-workload --timeout=180s
kubectl apply -k k8s/
```

## O que aconteceu

O pod novo ficou em `ImagePullBackOff` e o rollout não avançou. As duas réplicas antigas continuaram prontas e atendendo. O `rollout undo` voltou à imagem 1.1.0 e removeu o pod inválido. Um laço de uma requisição por segundo registrou 80 respostas 200 em 80 segundos, cobrindo a tentativa e o rollback.

## Decisões

A imagem inexistente foi usada de propósito para produzir uma falha controlada, sem alterar o código nem o Docker Hub. O `kubectl apply -k` seguinte atualizou a anotação `last-applied`, que o `undo` não altera.

## Problemas

O `rollout undo` avisou que a anotação `last-applied-configuration` ficaria desatualizada. O aviso foi tratado com `kubectl apply -k` logo depois.
